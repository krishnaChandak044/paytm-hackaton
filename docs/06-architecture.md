# 06 — Technical architecture and integration boundaries

## Reference architecture

1. **Authorised data connectors** receive eligible Paytm transaction/refund/settlement events. An optional regulated/approved connected-account integration receives bank data only within a merchant's active consent. All connectors carry source and time metadata.
2. **Event normaliser** maps provider-specific events to stable internal money events, deduplicates and preserves raw source references. Money remains in integer paise.
3. **Evidence ledger** stores verified facts, owner-confirmed obligations, model-generated candidates and corrections separately. It never overwrites the source event to make a model look correct.
4. **Pattern and forecast services** identify candidate recurring outflows, estimate future inflows by day, track calibration and data freshness, and create uncertainty-aware cash scenarios.
5. **Decision service** applies hard rules for scope, confirmation, eligibility, cost, consent and approvals. It ranks a small set of feasible options and can abstain.
6. **Language layer** transcribes/understands a merchant's request and explains a decision in the selected language. The language model receives facts and calculations; it does not authoritatively calculate balances or issue money movement instructions.
7. **Workflow and action gateway** prepare, approve, execute and reconcile external actions with idempotency and audit trails.
8. **Merchant surfaces** show private cards in Paytm for Business; optional Soundbox voice is conditional on actual supported integration and privacy-safe output.

## Essential data contracts

**Money event:** tenant ID, provider, source event ID, direction, amount, currency, occurred time, value time, status, payee token, order/transaction ID, settlement UTR if present, raw pointer and ingestion time. **Obligation:** owner-confirmed payee, amount, due date/time, recurrence rules if explicitly accepted, source, confirmation timestamp, version and current status. **Forecast:** horizon, known scheduled inflows/outflows, predicted inflow interval, covered accounts/channels, freshness, model version, calibration flag and generated time. **Decision:** input versions, resulting shortfall range, candidate actions, prerequisites, actual costs, reasons for rejected actions, approval requirement and expiry. **Action:** actor, exact payload, idempotency key, provider reference, status and audit events.

Do not infer a customer's purchased product from payment amount. Do not treat a settlement event as a new sale in addition to its originating transaction. Avoid floating-point money calculations. Local date and time must use the merchant's configured time zone; ‘Thursday’ is ambiguous without a date.

## Forecast implementation path

Prototype: a transparent rolling weekday baseline with low/high bands computed from backtests on synthetic or consented historical data. Research version: hierarchical or quantile forecasting with sparse-data shrinkage, event effects only where validated, and rolling-origin evaluation. Calibration monitoring is mandatory before probability language appears. An ‘80% range’ must be empirically supported by held-out data, not generated by an LLM. Regime shifts, holiday anomalies and merchant inactivity trigger uncertainty widening or fallback.

## Security and reliability

Separate read-only forecasting privileges from action privileges. Verify webhook signatures where supported, apply event deduplication, keep durable workflow state, use transactional outbox/inbox patterns for external sends, and reconcile unknown outcomes before retries. Protect approval tokens against reuse and bind them to exact action versions. Maintain audit records of model version and evidence at decision time. Alert on connector failures and stale balances. Use least-privilege staff roles and a private display for sensitive cash numbers.

## Integration reality

Public pages demonstrate that Paytm has merchant reports and several settlement options [S2–S3]. They do not grant hackathon developers access to internal merchant feeds, Soundbox firmware or action APIs. Account Aggregator is a consent-based regulated framework [S4], and access requires the right participating entities and agreement. A realistic prototype should simulate data connectors clearly and make integration points explicit. Production design requires Paytm engineering, risk, security, legal, and partner review.

## Unit economics and scale

Most processing should be event-driven and deterministic. Run expensive language-model inference only on merchant questions or ambiguous obligations. Batch forecasts and alert scoring where freshness permits. Store structured evidence rather than large repeated prompts. Measure cost per active merchant, per valid warning, per resolution, and per avoided interruption. A rollout gate should require alert precision and support economics, not merely model demo quality.
